# PDT: Portfolio v2

## Статус

Утверждён для поэтапной реализации.

## Цель продукта

Превратить персональную техническую визитку Андрея Балашова в коммерческое портфолио, которое за 20–40 секунд помогает потенциальному заказчику:

1. понять специализацию;
2. увидеть, какие задачи можно поручить;
3. оценить реальные проекты и инженерную компетентность;
4. перейти к обсуждению задачи в Telegram.

Вторая аудитория — технические заказчики, разработчики и партнёры, которые оценивают архитектуру, стек, GitHub и качество реализации.

## Принципы

- Клиенту показываем результат и понятные услуги; техническому читателю — доказательства компетентности.
- Не называем автора «начинающим» на первом экране: честность передаётся через точные статусы проектов и отсутствие неподтверждённых результатов.
- Сохраняем узнаваемую editorial/terminal-эстетику, фотографию, технологические акценты и спокойную типографику.
- Каждый смысловой блок отвечает на один вопрос пользователя и ведёт к контакту.
- Любое фактическое утверждение о статусе, результате, клиенте или метрике должно быть подтверждено до публикации.

## Позиционирование

**Категория:** веб-разработка и AI-автоматизация.

**Ценностное предложение:** современные сайты, веб-приложения и автоматизация для бизнеса — от лендинга и доработки существующего проекта до сервисов с базой данных, Telegram-ботов и AI-интеграций.

**Основное действие:** «Обсудить проект».

**Вторичное действие:** «Посмотреть работы».

## Информационная архитектура

Одностраничный сценарий:

1. Hero — кто, что делает, для кого, основной CTA.
2. Услуги — типы задач, которые можно поручить.
3. Избранные проекты — доказательства через задачу, решение, роль, стек и текущий статус.
4. Процесс работы — понятный путь от запроса до результата.
5. Об исполнителе — инженерный подход без повторения Hero.
6. Контакт — короткое приглашение и Telegram.
7. Footer — навигация, GitHub и актуальный год.

## Экран 4. Процесс

**Заголовок:** `Как строится работа`

1. **Задача** — уточняем цель, пользователей, ограничения и критерии готовности.
2. **Решение** — фиксирую структуру, технический подход, этапы и ожидаемый результат.
3. **Разработка** — показываю прогресс небольшими проверяемыми итерациями.
4. **Запуск** — проверяю сборку, адаптивность и публикацию, передаю результат и документацию.

## UX и адаптивность

- Основной CTA виден без прокрутки на типовом мобильном и desktop-экране.
- Якорная навигация работает с клавиатуры и не перекрывается интерфейсом.
- Интерактивные элементы имеют различимые hover/focus-состояния.
- Анимация отключается при `prefers-reduced-motion`.
- Контраст, семантические заголовки и подписи проходят отдельную проверку.
- На ширине 320 px нет горизонтальной прокрутки.

## Нефункциональные требования

- Статический экспорт для GitHub Pages сохраняется до отдельного решения о хостинге.
- Production-сборка должна завершаться успешно на Node.js 20.
- Контент и данные проектов отделяются от тяжёлой JSX-разметки по мере реализации.
- Производительность, accessibility и метаданные проверяются перед слиянием реализации.
- Схема публикации должна иметь один документированный источник истины.

## Метрики успеха

На первом релизе без аналитики:

- пользователь понимает специализацию и набор услуг по первому экрану;
- CTA к Telegram доступен из Hero и финального экрана;
- каждый проект содержит проверяемую структуру кейса;
- build и проверки проходят в PR;
- опубликованная версия сверена после деплоя.

Подключение аналитики и сбор количественных метрик требуют отдельного решения о приватности и инструменте.
